## 1단계 — 접근 제어와 관리 API

도메인 모델·DB 제약(slug 형식·유일·불변, `SeriesOrder` CHECK), 호스트·IP·CSRF 3겹 접근 제어, 비밀번호 로그인과 세션 폐기(절대 수명·해시 지문·epoch), 글·시리즈·태그 관리 API.

구현 중 계획이 틀린 것으로 드러난 것:

- **로그인 속도 제한기가 원시 경로 문자열로 파티션을 골랐습니다** — 끝에 슬래시를 붙인 `/api/auth/login/`으로 우회됐습니다. 엔드포인트 메타데이터로 고르도록 바꿨습니다.
- **IP 검사가 속도 제한보다 뒤에 있었습니다** — 허용 IP 밖의 요청이 로그인 전역 한도를 소진해 작성자를 잠글 수 있었습니다. 순서를 뒤집었습니다.
- `appsettings.json`의 빈 문자열 기본값이 `??` 널 병합을 통과해 "설정 없음"을 잡지 못했습니다.

## 2A단계 — 마크다운과 첨부

Markdig 파이프라인(raw HTML 비활성 → URL 정책 → 서버 측 강조 → HTML 허용 목록 정제), `POST /api/preview`, 이미지 첨부(시그니처 판정·메타데이터 제거·내용 주소 저장).

- **가장 큰 교훈: 계획을 그대로 옮긴 코드는 매번 통과했지만, 계획 자체가 틀려 있었습니다.** 측정하지 않고 쓴 문장이 결함의 원천이었습니다(계획 결함 16건).
- **Markdig 파서 자체가 초선형 비용**을 냅니다 — 적대적 200KB 입력에서 인라인 약 8.5초, 블록 약 6.6초(동기·취소 불가). 강조기에 시간 예산을 걸어도 파서는 남습니다. → 2B의 렌더 게이트·캐시로 덮었습니다.
- 메타데이터 제거기를 **기본 거부**(허용한 블록만, 모양까지 검사)로 다시 설계했습니다. 디코딩하지 않으므로 못 막는 잔여 표면 5종은 스펙에 명시하고 크기 상한·`nosniff`·sandbox CSP로 완화했습니다.
- 첫 Linux CI 실행에서 **절대 시간 상한을 둔 테스트가 깨졌습니다**(로컬 0.8초 → CI 7.2초). 이후 시간은 `TimeProvider`로 주입하고 비율로 단언합니다.

## 2B단계 — 공개 사이트

공개 Razor 페이지(목록·글·태그·시리즈·검색), Atom·sitemap·robots, 보안 헤더, 호스트 필터, 공개·검색 속도 제한, 읽기 전용 DB 연결(`statement_timeout`), 렌더 게이트와 캐시, 첨부 정합성(advisory lock·고아 청소).

- **최종 리뷰에서 실제 Production 호스트를 HTTPS로 직접 찔러, 인메모리 TestServer 579개가 놓친 결함 3건을 찾았습니다.**
  - 호스트 필터의 400이 프레임워크 HTML 본문을 실어 보냈다(그 응답은 앱 미들웨어 바깥이라 CSP·`nosniff`가 없다) → 본문을 껐다.
  - `publish` 출력의 `wwwroot`에 `.gz`·`.br` 사본이 생겨 `/css/site.css.gz`가 200이었다 → `CompressionEnabled=false`.
  - 경로 값이 공백뿐일 때(`/tags/%20`) MVC 바인딩이 `string` 매개변수를 **null**로 넣어 NRE → 500 → 핸들러를 `string?`로 받고 첫 줄에서 404.
- 그 밖에 계획 결함 23건, 내린 판정 28건. 이때부터 "테스트 스위트가 통과했다"와 "실제 호스트가 그렇게 응답한다"를 다른 명제로 취급합니다.
- 로컬 프로브가 평문 HTTP에서 변조된 응답을 보여 준 일이 있어(이 기계의 광고 차단기가 HTML과 CSP 헤더를 다시 씀) **실제 호스트 프로브는 HTTPS로만** 한다는 규칙이 생겼습니다.

## 3단계 — 관리 에디터 SPA

React 19 + Vite + CodeMirror 6로 글·시리즈·태그·첨부 관리 화면, sandbox iframe 미리보기, 임시본, 409 비교 화면. 실제 백엔드를 띄우는 Playwright E2E 8개와 CI 잡 둘(`web`·`web-e2e`)을 붙였습니다.

- **보안 통제 자체가 결함의 원천이었습니다.** 소스 가드(금지 패턴 검사)가 주석 제거 단계에서 **실제 코드를 삼켜** 그 구간의 위반을 놓쳤습니다. 세 라운드에 걸쳐 고쳤고, 그 과정에서 내가 내린 판정 하나(R5: 줄 주석을 먼저 지운다)가 틀려 뒤집혔습니다. 최종 형태는 TypeScript 파서로 리프 토큰의 trivia만 지우고, 지운 위치가 어떤 토큰 안에도 없다는 것을 독립 파싱으로 교차 검증합니다.
- 테스트 하네스의 "표에 없는 호출은 실패한다"는 단언이 **거짓**이었습니다(그 경로가 실제로 실패시키지 않았습니다).
- 최종 리뷰가 실제 호스트에서 5건을 더 찾았습니다: 디바운스 창 안의 입력이 세션 만료·화면 이탈 때 사라짐, 비밀번호가 mutation 변수로 캐시에 남음, SPA 라우트 `/attachments`가 개발 프록시의 접두사 매칭 때문에 백엔드로 끌려감, 보통 속도의 글쓰기로도 미리보기가 429에 닿음, 라우트 오류 경계 없음.
- 브라우저 차이도 실측으로 확정했습니다: Firefox는 `about:srcdoc` 문서의 CSP `'self'`를 부모 출처로 보지 않아 미리보기의 CSS·이미지가 전부 차단됩니다 → 출처를 명시합니다.

## 4단계 — 배포 (병합 완료, PR #5, 2026-09-23)

브랜치 `feature/blog-deploy`. 계획을 쓰기 전에 저장소 밖 복사본에서 이미지·compose·Caddyfile·백업 복원·스택 E2E를 **실제로 띄워 16가지를 측정**하고(S1~S16), 그 결과로 계획을 썼습니다. 그럼에도 리뷰가 그 위에서 더 찾아냈습니다.

Task 1~6을 브랜치에서 모두 마쳤습니다: 공개 조회 전용 DB 롤과 헬스체크 CLI(Task 1), Caddyfile과 이미지 둘(Task 2), compose·DB 롤 초기화·스택 스모크(Task 3), 백업/복원과 운영 문서(Task 4), 스택 대상 브라우저 E2E와 CI `deploy-smoke` 잡(Task 5), 스펙·README·`docs/`·CLAUDE.md/AGENTS.md as-built 반영(Task 6). 최종 리뷰(실제 스택 공격) 뒤 PR #5로 master에 병합됐습니다(2026-09-23). 첫 Linux CI 실행(deploy-smoke)이 통과했습니다(Windows에서 통과한 것이 Linux에서 처음 깨진 전례가 있어 게이트로 취급했습니다).

리뷰가 잡은 대표적인 것:

- `REVOKE … FROM {role}`은 **`PUBLIC` 의사 롤에 준 권한을 회수하지 못합니다** — 그 경로로 공개 롤이 `AdminState`를 읽고 썼습니다(실측).
- 스키마 전체를 대상으로 회수하면 **관리 롤이 비 슈퍼유저인 운영 형태에서 남의 소유 테이블 하나 때문에 기동이 막힙니다**. 테스트 하네스가 슈퍼유저로 접속하기 때문에 이 결함은 초록불로 지나갔습니다 → 비 슈퍼유저 소유자 롤로 도는 회귀 테스트를 추가했습니다.
- Caddy의 오류 응답 경로는 라우트의 지연 응답 래퍼를 거치지 않아 `Server` 헤더 삭제가 무효였습니다(405·413·502에서 노출). 두 도메인 밖 Host로 오는 요청(평문·TLS 폴백 둘 다)에도 같은 이유로 `Server`가 남아 폴백 사이트 블록에서 따로 지웠습니다.
- Caddyfile 헤더를 지키는 가드가 **위치 단언**이라, 헤더 블록을 다른 위치로 옮기는 변경을 잡지 못했습니다(테스트는 5/5 통과하는데 실제 응답의 보안 헤더 7개가 전부 사라짐).
- `edge` 네트워크가 `internal`이 아니어서 **api 컨테이너가 인터넷으로 직접 나갈 수 있었습니다**(실측) → `public`/`edge`/`db` 3망으로 나눠 api를 격리했습니다.
- 스모크의 DB 롤 검사가 `127.0.0.1`로 붙어 pg_hba의 `trust` 줄을 타는 바람에 **비밀번호를 전혀 검증하지 않았습니다**.
- 운영 문서가 처음 제시한 DB 비밀번호 변경 절차(인라인 `ALTER ROLE … PASSWORD`)는 실패하면 **postgres 로그에 평문 비밀번호를 남겼습니다** → 클라이언트에서 SCRAM 검증자를 계산해 보내는 `\password` 대화형 절차로 교체했습니다.
- 스모크의 허용 IP 목록이 Docker의 동적 게이트웨이 주소에 의존해 **기동마다 값이 달라질 수 있었습니다**(실측: 세션마다 다른 주소 관측) → 스모크 전용 compose에서 `public` 서브넷을 고정했습니다.
- Firefox에서 첨부 이미지가 로드되기 전에 화면을 새로고침해 이미지가 깨지는 **레이스**가 간헐적으로 났습니다 → 이미지 로드를 기다린 뒤 새로고침하도록 고쳤습니다.

측정으로 확정한 좋은 소식도 있습니다: ACME HTTP-01은 명시 `http://` 블록·IP 허용 목록과 공존합니다(실제 발급으로 증명). 자세한 내용은 [배포 구성](deployment.md).

## 문서화 하네스 (병합 완료, PR #6, 2026-09-25)

브랜치 `feature/doc-harness`. 코드가 Source of Truth인 **신규 개발자용 기술 문서**를 사람 손 없이 만들고 유지하기 위해 `doc-harness/`(TypeScript)를 만들었습니다. `claude -p`를 읽기 전용 도구만 가진 자식 프로세스로 띄워 Inventory → Architecture → 기능 발견·심층 분석 × 29 → Data/API → 실패 이력 → 횡단 분석 → 문서 생성 → 검증 루프를 돌고, 결과를 Run 트랜잭션(staging → 검증 → 원자 교체 → baseline)으로 발행합니다. 이후에는 baseline 대비 변경분(커밋·스테이지·미커밋·untracked)만 증분 갱신하고, 사람이 고친 섹션은 보존합니다. 모든 다이어그램은 Mermaid 인라인이며 jsdom 파서로 문법을 검증합니다.

실제 저장소에 두 번 발행했습니다: INITIAL(run-0001, 문서 61개·Mermaid 101개, 약 $347)과 INCREMENTAL(run-0002, 소스 한 줄 변경 → 기능 2개·문서 15개·다이어그램 3개만 갱신). 결과는 [생성 기술 문서](generated/README.md)에 있고, 검증기가 남긴 지적 61건은 [19_UNKNOWN_AND_TODO](generated/19_UNKNOWN_AND_TODO.md)에 기록돼 있습니다.

실전에서 잡은 대표적인 결함(전체 17건은 [실전 보고서](../plan/doc_harness_0923.md) 7절):

- 프롬프트에 **오늘 날짜·분석 상태·Map 순서**가 섞여 재개할 때마다 캐시가 깨지고 기능 29개를 다시 분석했습니다($45) → ISO 날짜를 자리표시자로 바꾼 안정 해시, 정렬, working tree diff에서 하네스 자신의 변경 제외.
- 결정적 검사기의 **오탐 300여 건**(개념 노드, 짧은 경로 표기, "…은 없다" 같은 부정문)이 수정 루프를 폭주시켰습니다 → 확신할 수 있는 것만 차단, 나머지는 경고.
- 교차 일관성 검사가 `GET, HEAD` 복합 메서드를 한 토큰으로 봐 API 표 누락 10건을 오탐했고, LLM 수정 루프로는 풀 수 없는 차단이 됐습니다 → 메서드별로 펴서 대조.
- 사용량 한도 오류를 3회 재시도하고 남은 기능도 계속 시도했습니다 → 즉시 실패, 워커 풀 중단, FAILED Run 재개.
- "회차 이력이 없어 재개마다 재검증 $30이 든다"는 판정은 **틀렸습니다** — Fake 러너로 중단→재개를 재현하니 실패 항목만 다시 돌았습니다(캐시). 실제 원인은 재개 사이에 하네스 코드를 고쳐 문서가 다시 렌더된 것이었습니다.

교훈: 입력 해시에 들어가는 모든 것은 결정적이어야 하고, 비싼 단계(LLM 검증)는 가장 뒤에 한 번씩만 두고 싼 단계(결정적 검사)를 앞뒤로 반복하며, 결정적 차단이 0이면 잔여 LLM 지적을 기록하고 발행하는 것이 한도가 있는 환경에서 끝을 보는 방법이었습니다.

## MySQL 전환 (2026-09-26, 브랜치 `feat/mysql-migration`, 병합 대기)

저장소를 PostgreSQL에서 **MySQL 8.4로 완전 교체**했습니다(둘을 함께 지원하는 구성은 만들지 않았습니다). PostgreSQL은 연결 문자열 수준을 넘어 읽기 전용 공개 롤·시작 세션 매개변수·권고 잠금·`xmin`·정규식 CHECK 같은 **보안 통제의 구현 수단**이었으므로, 이번 전환은 그 통제를 하나씩 대체하고 다시 증명하는 작업이었습니다.

Phase 0 스파이크에서 처음 고른 Oracle `MySql.EntityFrameworkCore` 10.0.9가 no-go 판정을 받았습니다(`UseCollation`·`IsDescending`이 생성 DDL에서 빠지고, `Like` 이스케이프가 잘못된 SQL을 만들었습니다). 대신 **Pomelo `Pomelo.EntityFrameworkCore.MySql` 9.0.0**(EF Core를 9.0.20으로 하향)으로 다시 스파이크해 go 판정을 받았습니다.

주요 대체: 공개 조회 롤의 GRANT를 앱이 기동마다 적용하고 `SHOW GRANTS`로 스스로 검증(불일치·초과 시 기동 실패, fail-closed) · 공개 연결이 열릴 때마다 세션에 `transaction_read_only`·`max_execution_time`을 거는 인터셉터 · `xmin` 대신 앱이 관리하는 `Version` 컬럼(모든 UPDATE 경로가 +1해야 함을 아키텍처 테스트로 강제) · `pg_advisory_lock` 대신 `GET_LOCK`(이름에 DB 해시로 네임스페이스 분리) · MySqlConnector가 트랜잭션마다 강제하는 REPEATABLE READ를 인터셉터로 READ COMMITTED로 되돌림(서버 플래그만으로는 트랜잭션 밖 문장이 여전히 REPEATABLE READ) · SqlState 대신 `MySqlException.Number` 기반 단일 오류 분류기.

- 서수 순서 삽입만으로 태그 upsert의 데드락(1213)이 나지 않음을 부하 테스트로 확인해 재시도 로직을 추가하지 않았습니다(순서를 없애자 3/3 재현).
- init 스크립트의 최초 구현이 비밀번호를 `sed` 치환 인자로 넘겨 컨테이너 `ps`/`/proc/*/cmdline`에 노출시켰습니다 → 셸 내장 `printf`로 SQL을 직접 조립하도록 바꿨습니다.
- root를 `MYSQL_ROOT_HOST=localhost`로 소켓 전용으로 잠갔습니다(리뷰 권고, 원격 root 로그인 경로를 아예 없앰).
- CI push 트리거가 `feature/**`만 받아 `feat/mysql-migration` 브랜치에서 CI가 한 번도 돌지 않은 것을 발견해 `feat/**`를 추가했습니다.
- 통합 테스트 픽스처가 Pomelo가 연결 문자열에 덧붙이는 `Allow User Variables=True;Use Affected Rows=False` 때문에 원시 `MySqlConnection`과 EF가 서로 다른 풀을 쓰는 것을 놓쳐, 테스트가 엉뚱한 풀을 비우고 있었습니다 → EF가 실제로 만드는 연결 문자열을 그대로 풀 키로 쓰도록 고쳤습니다.
- CHECK 제약의 정규식 끝 앵커(`\z`)를 런타임 값으로는 구별할 수 없는 케이스가 있어(64자 hex + 개행이 길이 제한에 먼저 걸림), `information_schema.CHECK_CONSTRAINTS`를 읽는 정적 검사로 증명 방법을 바꿨습니다.

CI 4개 잡(test·web·web-e2e·deploy-smoke)이 모두 green입니다. 이 PC는 Hyper-V가 포트 4173을 배타 예약해 로컬 브라우저 E2E를 막으므로 CI가 대신 판정합니다. 설계·실측·판정 전체는 [설계 스펙](../plan/mysql_migration_0926.md)과 태스크별 보고서(`.superpowers/sdd/mysql_migration_impl_0926/`)에 있습니다.

## 이 저장소가 일하는 방식

작업은 **브레인스토밍 → 계획 → 실행 → 리뷰 → 보고서** 순서로 돌고, 각 단계가 파일로 남습니다.

- 계획은 `docs/superpowers/plans/`에, 실행 결과 보고서는 `plan/`에 둡니다. 보고서에는 **"질문 없이 내린 판정"** 표(결정 / 이유 / 틀렸을 때의 비용)가 들어갑니다.
- 계획대로 구현한 뒤 **리뷰어가 계획 자체를 의심**합니다("계획 코드가 틀렸을 수 있다 — 직접 공격하고 측정하라"). 실제로 매 단계에서 계획 결함이 나왔습니다.
- 리뷰어는 저장소 밖 복사본에서만 측정합니다(작업 트리를 오염시키지 않기 위해).
- 새 테스트는 **사보타주로 실패를 확인**합니다 → [테스트](testing.md).
- 설계 국면에서는 OpenAI Codex CLI를 read-only 교차 검증자로 부릅니다 → [개발 하네스](harness.md).
